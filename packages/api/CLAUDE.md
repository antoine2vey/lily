# packages/api

The Lily backend is an Effect `HttpApi` on Bun. One process, started by `src/index.ts`, serves the HTTP API on port 3000 and runs every scheduler, worker and subscriber. The core tables belong to the four bounded contexts in `src/contexts/`. Every change to a care, a schedule, a plan, a plant's life, a reminder, a canopy, a delegation or a vacation goes through its context, and `src/__tests__/architecture/context-boundaries.test.ts` fails on a direct write from anywhere else.

## Commands

Run every command from the monorepo root.

| Command | What it does |
|---|---|
| `bun run --filter=@lily/api dev` | Starts the server on port 3000 and restarts it on every change |
| `bun run --filter=@lily/api tsc` | Typecheck |
| `bun run --filter=@lily/api test` | Vitest over `src/__tests__`, run on Bun (`bun --bun vitest run`), the runtime production uses. Node and Bun give different zone ids for `GMT` (`src/__tests__/runtime.test.ts`), so `src/__tests__/setup.ts`, the setup file of both vitest configs, fails every test file of either suite that starts on Node. `vitest.config.ts` excludes `src/__tests__/integration`, so no env file or `DATABASE_URL_TEST` turns those suites on here |
| `bun run --filter=@lily/api test src/__tests__/services/plants` | One directory or file |
| `bun run --filter=@lily/api lint` | Biome check |
| `bun run --filter=@lily/api lint:fix` | Biome with autofix |
| `bun run db:setup-test` | Applies the migrations to the test database and seeds the tiers |
| `bun run test:integration` | Every integration suite against the test database, one file at a time. It uses `vitest.integration.config.ts`, which includes only `src/__tests__/integration` |
| `bun run test:integration src/__tests__/integration/<file>` | One integration suite |

The last three read `.env.test.local` at the repo root. Set both `DATABASE_URL_TEST` and `DATABASE_URL` to the test database there. A suite runs only when `DATABASE_URL_TEST` is set, and `PgLive` from `@lily/db` connects with `DATABASE_URL`, so a suite with only the first fails on a `ConfigError`.

The knowledge search suite, `src/__tests__/integration/knowledge-search.integration.test.ts`, needs pgvector, so it runs only when `KNOWLEDGE_DATABASE_URL_TEST` is set instead. Point it at the compose `knowledge-db-test` service. The suite creates its own database there and migrates it with `packages/knowledge-db/scripts/migrate.ts`.

## Layout

- `src/server.ts` builds `ServerLive`, which registers every handler group and launches every scheduler, worker and subscriber as a `Layer.effectDiscard`. A new scheduler runs only after you add it there. `src/__tests__/architecture/schedulers-launched.test.ts` fails on an exported `createScheduler` or `createDrainableScheduler` that `src/server.ts` does not name. `src/index.ts` runs `ServerLive` with telemetry and logging, so tests can import `ServerLive` without starting the process.
- `src/api.ts` composes the `HttpApi`. Add each group with `.prefix(API_PREFIX)` from `@lily/shared`, so it serves under `/api/v1`. `HealthApiGroup` and `InternalApi` stay at the root. `src/middleware/legacy-api-prefix.ts` keeps `/api/...` as a permanent alias of `/api/v1/...`, because installed app builds and the RevenueCat webhook still call it.
- `src/services/<domain>/` has one shape, as in `src/services/plants/`. `src/services/plants/api.ts` defines the `HttpApiEndpoint`s, `src/services/plants/handlers.ts` is the `HttpApiBuilder.group`, `src/services/plants/endpoints/` has one function per endpoint and `src/services/plants/helpers/` the rest. A domain with routes has no `service.ts`, and its handlers call endpoint functions directly. Only an infrastructure service with no routes, such as `src/services/ai/service.ts`, defines one.
- `src/contexts/` holds `care`, `reminders`, `canopy` and `absence`, each in a section below. Import a context only through its index, `@lily/api/contexts/<name>` (`src/contexts/care/index.ts` for Care), and never from a module that context loads. The boundary test fails on a deep import and on a load cycle.
- `src/kernel/` holds what the contexts share: `src/kernel/transact.ts` (the `Transaction` service), `src/kernel/permit.ts` (permits), `src/kernel/owner.ts` (`OwnerHeld`), `src/kernel/outbox.ts`, `src/kernel/locks.ts`, `src/kernel/transition.ts` and `src/kernel/user-dependents.ts` (`USER_DEPENDENTS`, the policy of every foreign key to `users` at each exit). The kernel declares a permit and `OwnerHeld` but exports no way to build one. `src/services/plants/helpers/with-plant-access.ts` builds a `PlantPermit`, `src/services/care-plans/helpers/with-care-plan-auth.ts` a `PlanPermit` and `src/services/plants/helpers/owner-lock.ts` an `OwnerHeld`, each after its check. A test builds one through `src/__tests__/mocks/permits.ts`. `src/__tests__/architecture/context-boundaries.test.ts` fails on a plain (`as X`) or angle-bracket (`<X>x`) cast whose target type names `PlantPermit`, `RecordPermit`, `PlanPermit`, `OwnerHeld` or `Seen` outside its module, a wrapper such as `ReadonlyArray<PlantPermit<A>>` included, on any `as never`, and on a production file whose text names `__tests__/`. It reads text, so it misses a cast through a type alias, an `import()` type, a utility type such as `Parameters<typeof need>[0]`, a generic cast helper, an `any` such as the result of `JSON.parse`, and a cast whose target type spans lines. A spread keeps the brand of a permit and of a `Seen` row, so `{ ...permit, plantId }` is a permit for another plant and `{ ...row, chatMessageId }` is still `Seen`. No context imports `CurrentUser` from `src/services/auth/middleware.types.ts`, so a context learns its actor from the permit or the user id it is given.
- `src/layers/index.ts` builds `AppLive` from every repository, context and infrastructure layer. `CODING_STANDARDS.md` has the rule that the program root provides it once. `src/layers/outbox.ts` lists every outbox consumer in `appConsumers`. A consumer runs only when `appConsumers` lists it, and the tests build their outbox from the same list.
- `src/repositories/` is the read side, plus the writes no context owns. A repository returns `null` for a missing row, and the endpoint turns that into its not-found error. Every write to the `notifications` table is in `src/repositories/notification.repository.ts`. Only delivery (`src/services/notification-scheduler/` and `src/services/helpers/schedule-notification.ts`) moves a notification by id or drops it, with methods such as `claimForDelivery`, `deferUntil` and `deleteByIds`.
- `src/events/` holds the EventBus events. `src/events/care-forwarder.ts` turns Care facts into the events the app listens to.
- `models/` holds the Quint models of the concurrent protocols, such as `models/la-start.qnt` for the Live Activity start guard and `models/usage-reservation.qnt` for the monthly usage reservation. Each action is named after the function it mirrors. `scripts/check-models.sh` lists every model with the verdict it must give, and CI runs it. When you change a function a model names, change the model, and the integration test that replays its runs, in the same PR.
- `src/probes/` holds one-off programs CI runs inside the prod image, such as `src/probes/zone-rules.ts`, which builds the zone-rules guard against the real Bun. Nothing imports them.
- `src/scripts/` holds one-off programs an operator runs by hand inside the prod image, such as `src/scripts/sweep-orphans.ts`. Their logic lives in a sibling module the tests import, such as `src/scripts/orphan-sweep.ts`.
- `src/__tests__/` mirrors `src/`, so the tests of `src/services/plants/` are in `src/__tests__/services/plants/`. `src/__tests__/architecture/` holds the boundary test, `src/__tests__/integration/` the suites that run on a real Postgres, `src/__tests__/mocks/` the repository mocks and `src/__tests__/fixtures/` the test data.

## Rules

- **Handlers call endpoints.** A handler checks access and passes what it got to the endpoint function.

  ```typescript
  export const PlantsApiLive = (api: Api) =>
    HttpApiBuilder.group(api, 'plants', (handlers) =>
      handlers
        .handle('getPlant', ({ params: { id } }) =>
          withPlantAuth(id, 'view').pipe(
            Effect.flatMap((plant) => findPlantById(plant)),
            withInfraErrorsAsDefect,
          )
        )
    )
  ```

- **`withPlantAuth`.** `withPlantAuth(id, action)` returns the plant when the caller's `PlantRole` may perform `action` per the table in `src/services/plants/helpers/plant-access.ts`. No role answers `PlantNotFoundError` with the same body as a missing plant. A role without the action answers `PlantNotAuthorizedError`. `withPermittedPlant` returns the plant and a `PlantPermit`, and `withPlantPermit` returns the permit alone. `withRecordPermit(id, add)` serves an endpoint that changes or removes a care or a photo, the correction of the last care included. It returns a `RecordPermit`. A role that may `curate` gets the `curate` permit. Any other role gets the `add` permit, which reaches only the records its actor added. The command, not the handler, compares the record's author with `coversRecordOf` from `src/kernel/permit.ts`, on the row it has locked. A record outside the permit answers `PlantNotAuthorizedError`. Use `Effect.flatMap` when the endpoint needs the plant and `Effect.andThen` for an auth-only check. An endpoint uses the plant it received and never fetches it again.
- **`Seen`.** A care plan or a diagnosis keeps its `chatMessageId` for its author only. Its success schema brands it with `seen` from `src/services/plants/helpers/seen.ts`, and only `seenByCaller` returns that type. `seenByCaller` reads the viewer from `CurrentUser`, so no caller can name the wrong one. A handler that sends a row without it fails `tsc` on `Brand<"Seen">`. Decoding through `seen` would also make a `Seen` row, so the architecture test lets only the two `api.ts` files import it. Any other file imports `seenByCaller` or the type `Seen` by name. A namespace import or an `import()` of `seen.ts`, and a `Seen` brand made outside it, fail.
- **Schedulers use `createScheduler()`** from `src/services/helpers/create-scheduler.ts`. It logs a failed tick and keeps going, so a scheduler never crashes the server.

  ```typescript
  export const startMyScheduler = createScheduler({
    name: 'my-scheduler',
    interval: '1 hour',
    runOnStartup: true,
    task: myTask,
  })
  ```

- **A stored time zone never reaches Postgres.** `users.timezone` and `canopies.timezone` hold a canonical IANA zone, the `TimeZone` schema of `@lily/shared`. Postgres reads the tzdata of its own image, a separate list from Bun's. A zone missing from it fails the whole query in `AT TIME ZONE`, and a zone both know can still place local midnight at a different instant. Compute the boundary with the date helpers of `@lily/shared` and bind the instant, as `countTodayByUser` does in `src/repositories/care-log.repository.ts`. `src/__tests__/architecture/sql-time-zones.test.ts` fails on `AT TIME ZONE` with any zone other than `'UTC'`, and on `timezone(`, `make_timestamptz(` and `SET TIME ZONE`. It does not catch a zone passed to `date_trunc`, `set_config`, `generate_series` or `date_add`, a zone concatenated into a text cast such as `(day || zone)::timestamptz`, or the `SET timezone = ...`, `SET SESSION TIME ZONE` and `SET LOCAL timezone TO` spellings. Across the repository, `scripts/check-sql-time-zones.sh` fails CI on `AT TIME ZONE` with any zone other than `'UTC'` and on `pg_timezone_names`.
- **Background fibers in a layer fork with `Effect.forkScoped`.** A `forkChild` fiber is interrupted as soon as the layer finishes building, so the loop never runs. Wrap each step of a worker loop in `drainOnInterrupt`, so a shutdown lets the step in flight finish.
- **Naming.** Requests are `{Entity}CreateRequest` and `{Entity}UpdateRequest`. Responses are `{Entity}ListResponse` and `{Entity}Response`. Data types are `Create{Entity}Data` and `Update{Entity}Data`.
- **EventBus or MessageQueue.** EventBus (Redis pub/sub) is for fire-and-forget events, such as achievements. MessageQueue (Redis lists) is for work that must happen at least once, such as notification delivery. Publish an event with `publishWithRetry()` from `src/events/retry-policy.ts`.
- **A write that names a user outside the contexts holds no account.** A room, a device token or a chat message is such a write. When a hard deletion of that account commits under it, the write breaks the foreign key to `users` and the handler dies on a `SqlError`. The `Authentication` middleware in `src/services/auth/middleware.impl.ts` answers that case for every such handler. When the handler dies on a `SqlError` and the account of `CurrentUser` no longer exists, the request answers the `UnauthorizedError` its next request would get, and the defect is logged at error level. Every other defect still answers 500. The middleware fixes the answer, so such a writer needs no account hold. `AdminAuth` has no such rule.
- **An image a client names goes through `src/services/helpers/client-image.ts`.** `readClientImage` reads the reference into the caller's own private upload or `Untrusted`. `readChatImageKey` reads a chat `imageKey` into the key of an upload in the caller's folder for that conversation, and the chat stream answers 404 to any other key. A column that holds a stored object takes a `StoredObjectRef`, which only these readers, `readIssuedAvatar` and the upload methods of `GCSService` return, so `tsc` fails on a client string written there. Sign the key again before an AI call. A new endpoint that takes an image takes an upload, not a URL.
- **Tests are mandatory for new features.** Mock at the repository level, not the database. Read a typed failure with `Effect.runPromiseExit` and `failureOf` from `@lily/shared/testing`, and a defect with `defectOf`. Each throws on any other exit, so the assertion cannot pass by skipping. `lint/assert-which-error.grit` fails a test that asserts only `Exit.isFailure`.

  ```typescript
  const exit = await Effect.runPromiseExit(
    getUserSettings().pipe(
      Effect.provide(
        Layer.mergeAll(
          createMockUserRepository([...mockUsers]),
          createMockCareLogRepository([]),
          createMockCurrentUser({ id: 'non-existent' })
        )
      )
    )
  )
  expect(failureOf(exit)).toBeInstanceOf(UserNotFoundError)
  ```

## Transactions

An operation that is only right inside its caller's transaction requires the `Transaction` service of `src/kernel/transact.ts`, so it does not compile outside one. Every store lock and `apply`, `Absence.holdForDeletion` and `releaseForDeletion`, `Canopy.holdAsMember`, `Reminders.request` and `outbox.append` require it. `transact` provides it. So does `transactQuietly`, which wakes no relay and is for a body that appends nothing to the outbox. Do not provide `Transaction` anywhere else, and do not capture it in a layer. A test that calls such an operation on its own wraps it in `transactInMemory` from `src/__tests__/mocks/transaction.ts`.

A lock that waits is taken through `src/kernel/locks.ts` and nowhere else. It locks rows in id order and dies with `LockOrderDefect` when a transaction asks for a kind below one it already holds on `LADDER` in `src/kernel/ladder.ts`, so the order in which a transaction first takes each kind is that list. An `UPDATE` of an account row is written by `writeAccount` of the same file, for one user id and from the values the caller gives it, so the lock it takes without asking climbs the ladder too. That lock is `FOR UPDATE` when a value belongs to a unique column of the table, such as the email or the name, and `FOR NO KEY UPDATE` otherwise. `src/__tests__/architecture/context-boundaries.test.ts` fails on lock syntax in any other file, on an account update in any other file, written with the query builder or as SQL text, and on an import that renames the `users` table. The ladder does not see the lock of any other `UPDATE` or `DELETE`, a second statement on a kind already held, or a `FOR KEY SHARE` pin of an account. That includes the pin the foreign key of an insert takes without asking, and one deadlock through such an insert is known (issue #384).

A status column is written by `src/kernel/transition.ts` and nowhere else. `src/__tests__/architecture/status-writes.test.ts` fails on any other write and lists the allowed ones.

An endpoint that answers with a row its command wrote reads that row in the same transaction. It wraps the command and the read in `transact`, or reads inside the body of `withOwnerLock`. The command's own transaction becomes a savepoint, so its locks hold until the read is done. A read made after the commit can find the row deleted by a request that waited for the command, and then answers 404 or dies. `src/__tests__/integration/read-back-races.integration.test.ts` has one race per endpoint.

An effect that is only right once the change is committed, such as the enqueue of a notification the worker then reads, is registered inside the transaction with `Transaction.afterCommit`. It runs after the outermost commit, so a caller may wrap the command in its own `transact`, and it is dropped when that transaction or one around it rolls back. Do not run such an effect after `transact` returns. Under a caller's transaction, that is before the commit. `Canopy.join`, `invite`, `leave`, `removeMember` and `leaveForDeletion`, and the delegation commands of `Absence`, enqueue their notifications this way.

## Stored objects

A write that drops a photo reference (a plant image, plant photo, care photo, avatar or chat image) runs inside `releasing` from `src/services/helpers/release-objects.ts`. It reads the references before the write, and after the commit it deletes each object that no column in `REF_HOLDERS` of `src/repositories/stored-ref.repository.ts` still points at and that its `Holder` owns. `REF_HOLDERS` is every `storedRef()` column of `@lily/db/schema` and every entry of `JSON_REF_HOLDERS`, and the orphan sweep reads the same list, so a column declared with `storedRef()` is honoured by both. A storage failure is logged and does not fail the request. The account purge deletes the owner's folder later. An endpoint that uploads before its write wraps the write in `releasingRefusedUpload`, which deletes the upload when the write is refused. It keeps the upload on a `SqlError`, because the commit may have gone through. `src/__tests__/integration/released-objects.integration.test.ts` covers each endpoint.

Objects orphaned before `releasing` existed are removed by hand with `bun run --filter=@lily/api sweep:orphans`. It lists both buckets, reads every reference with `StoredRefRepository.everyRef`, and prints a verdict per object: `referenced`, `inside-grace` (younger than `--grace`, default 7 days), `foreign` (a key layout the API never writes) or `orphan`. It deletes nothing without `--apply`. With `--apply` it deletes the orphans in batches of `--batch` (default 100), logging each outcome, and refuses when no reference was read, when a bucket holds objects that no reference names, or when a reference mentions a bucket but names no object. `namedObjects` in `packages/shared/src/services/file/stored-object.ts` turns a stored key or URL, in any shape the columns have held, into the objects it names.

A write that copies an existing reference into another row first locks the row it copies from, in the same transaction. Otherwise a deletion of that row can commit and delete the object before the copy is visible to it. `createDiagnosisTool` copies a chat photo this way: it calls `DiagnosisRepository.holdConversation` after `CarePlans.propose`, because removing a plant locks the plant before its conversations.

## Reminders

Care and overdue reminders are planned in `src/contexts/reminders` and nowhere else. Code that changes what they are planned from (a recipient's settings, a plant's `remindersEnabled`, the release of an account) calls `Reminders.request` with one or more `Dirty` values, such as `Dirty.Recipient({ userId })`, inside the transaction that makes the change. For the release of an account, that is the transaction `Canopy.leaveForDeletion` opens. The request commits with the change and is replanned after it, with retries, so a failed replan never rolls the change back. A change made through a `Care`, `Canopy` or `Absence` command needs no request. The context publishes a fact on its outbox topic, and Reminders replans what the fact makes stale.

Do not create, re-time, lock or delete a row of a reminder type outside the context. `NotificationRepository.create` and `deletePendingByUserIdAndTypes` reject those types at compile time, and `src/__tests__/architecture/context-boundaries.test.ts` fails on a new writer. Terms are in `CONTEXT.md`, section Reminders.

## Canopy

A canopy, its members, links, invitations and mutes are changed in `src/contexts/canopy` and nowhere else. The same holds for the owner of a plant or a room once the row exists. A caller runs one command of the `Canopy` service from `@lily/api/contexts/canopy`: `create`, `update`, `leave`, `removeMember`, `dissolve`, `leaveForDeletion`, `createLink`, `revokeLink`, `join`, `invite`, `withdrawInvitation`, `declineInvitation`, `sharePlant`, `unsharePlant` or `setMute`. The plant commands take a `PlantPermit` from `withPlantPermit`. The others take the id of the acting user.

Each command opens its own transaction, takes its locks through `CanopyStore.lockAndLoad`, applies the rules of `src/contexts/canopy/domain/decide.ts`, writes, records the notifications it owes and publishes what happened on the outbox topic `canopy`. Reminders consumes that topic and replans by itself, so no caller of a Canopy command calls `Reminders.request`. `CanopyRepository` is the read side. It has no write and no lock.

A command holds the account of every user its rows name until it commits, so a hard deletion of that account waits for it or the command finds no account. A member of the canopy the command holds is held by the canopy row. `leaveForDeletion` takes the per-user key of `lockUser` first, as `create` and `join` do, so the deletion always finds the canopy of a member and waits for its row. A user who is not a member yet is named in the `accounts` of the lock plan and read `FOR KEY SHARE`. Those users are the creator of `create`, the joiner of `join` and the invitee of `invite`. `create` then takes no other lock, and the other two take only invitation rows of a canopy they already hold. A missing account is a refusal. `create` answers the `UnauthorizedError` of a request with no account behind it, `join` answers `CanopyInviteNotFoundError` and `invite` answers `UserNotFoundError`. A new command that writes the id of a user who may not be a member names that user in `accounts`.

Do not write `canopies`, `canopy_members`, `canopy_invites`, `canopy_direct_invites` or `canopy_plant_mutes` outside `src/contexts/canopy/store.ts`, do not set `user_id` or `canopy_id` on an existing plant or room there either, and do not lock a canopy row. `src/__tests__/architecture/context-boundaries.test.ts` fails on each of these, and on an import of `src/contexts/reminders` from Canopy code. A new refusal does not compile until `errorOf` in `src/contexts/canopy/canopy.ts` gives it an error, and a new fact does not compile until `staleAfterCanopy` in `src/contexts/reminders/triggers.ts` says what it makes stale. Terms are in `CONTEXT.md`, section Canopy.

## Absence

A delegation is opened and changed, and a vacation is set, called off, started and ended, in `src/contexts/absence` and nowhere else. A caller runs one command of the `Absence` service from `@lily/api/contexts/absence`: `openDelegation`, `respondToDelegation`, `cancelDelegation`, `completeDelegation`, `setVacation`, `cancelVacation`, `advanceDelegations` or `advanceVacations`. The first six take the id of the acting user. The two schedulers call the last two at startup and then at their interval. An account deletion calls two more, `holdForDeletion` and `releaseForDeletion`, which open no transaction and run in the one `Canopy.leaveForDeletion` opened. Each due delegation or vacation gets a transaction of its own, so one that fails is counted and the next still runs. A delegation still pending at its start is due too. The tick cancels it and tells the owner with `delegation_canceled` and the param `unanswered`.

Opening a delegation is a paid feature. `src/services/delegation/endpoints/create-delegation.ts` calls `LimitChecker.checkDelegationAccess` before it runs `openDelegation`, and a free account gets a `LimitExceededError` for the feature `care_delegation`.

Each command opens its own transaction, takes its locks, applies the table `RULES` of `src/contexts/absence/domain/delegation.ts` or `src/contexts/absence/domain/vacation.ts`, writes, records the notifications it owes and publishes what happened on the outbox topic `absence`. Reminders consumes that topic and replans by itself, so no caller of an Absence command calls `Reminders.request`. `DelegationRepository` is the read side.

Do not write `care_delegations` or `delegation_plants` outside `src/contexts/absence/store.ts`, do not lock a delegation row outside it, and do not give `vacation_status`, `vacation_start` or `vacation_end` a value there either. Absence reads memberships through `CanopyRepository` and imports neither `src/contexts/canopy` nor `src/contexts/reminders`. `src/__tests__/architecture/context-boundaries.test.ts` fails on each of these. Canopy imports `src/contexts/absence` for `holdForDeletion` only, so `CanopyLive` is built over `AbsenceLive`. A new command or status does not compile until `RULES` has its cell, a new refusal until `src/contexts/absence/absence.ts` gives it an error, and a new fact until `staleAfterAbsence` in `src/contexts/reminders/triggers.ts` says what it makes stale. Terms are in `CONTEXT.md`, section Absence.

A vacation command locks the account row `FOR NO KEY UPDATE`, so it never waits on a care that only references the account. An account deletion takes the per-user key of `lockUser` first. An opening takes the key of each of its two users, so the deletion finds every delegation that names the account, and an opening behind it finds no account and is refused. The deletion then takes the same lock through `holdForDeletion`. A command on an existing delegation holds its row, which the deletion of either party waits for, so the notifications it records for them never name a deleted account. It then takes every plant its delete writes (`PlantScope.Leaver` in `src/contexts/canopy/store.ts`). Those are the plants of the canopy, the user's own, those the user created and those with a plan the user wrote.

Whether a caretaker tends a plant is one SQL condition, `tending()` in `src/repositories/helpers/tending.ts`. The delegation is active and the caretaker's account is reachable. Use it in every query that gives a caretaker access to a plant or picks who is reminded, in place of a comparison of `careDelegations.status` with `'active'`.

## Care

A care, a care schedule, a care plan and the life of a plant are changed in `src/contexts/care` and nowhere else. A caller runs one command of one of three services from `@lily/api/contexts/care`. All three write through one `CareStore` and publish on one outbox topic, `care`.

- `Care` records and edits cares and schedules: `record`, `recordOne`, `amend`, `remove`, `correctLastCare`, `setSchedules` or `moveDueDays`.
- `PlantLife` creates, buries, revives and removes a plant: `plant`, `bury`, `revive` or `remove`. Dead plants, below, has its rules.
- `CarePlans` proposes and runs a care plan: `propose`, `accept`, `dismiss`, `delete`, `tickStep`, `untickStep`, `dropStep`, `linkToDiagnosis` or `linkToMessage`.

A command on a plant takes a `PlantPermit` minted in `src/services/plants/helpers/with-plant-access.ts`. `Care.amend`, `Care.remove` and `Care.correctLastCare` take a `RecordPermit<'care'>`, and a `care` permit there reaches only the cares its actor performed (rule 7 of `CONTEXT.md`, section Care). In `src/contexts/care/domain/decide.ts`, `amendEntry` and `removeCare` are the only writers of `ReplaceCare` and `DeleteCare`, and each asks `coversRecordOf` first. A new command that changes a care goes through one of them. `CarePlans.propose` and `linkToDiagnosis` take the `PlantPermit<'chat'>` of the chat. The other plan commands take a `PlanPermit` from `withCarePlanAuth`. `PlantLife.plant` takes the `OwnerHeld` proof and the id of its creator, because the plant does not exist yet. `moveDueDays` and `linkToMessage` take no permit. `moveDueDays` serves the weather readjustment and Absence, and `linkToMessage` serves the chat save. No Care code reads the current user.

Each command opens its own transaction and locks the plant row, `FOR NO KEY UPDATE` in every command except `PlantLife.remove`, which takes it `FOR UPDATE`. A plan command locks the plant of its plan, so no command locks a plan row. A command whose rows name the acting user (`Care.record`, `recordOne`, `correctLastCare`, `CarePlans.propose` and `tickStep`) loads through `CareStore.lockAndLoadFor`, which reads that user's account row `FOR KEY SHARE` after the plant rows, never before. The foreign key of the row takes that lock at the write anyway, so the order against an account deletion is the same. The delete of the account waits for the command, or the command waits for the delete and then finds no account. It is then refused as `ActorGone` and answers `PlantNotFoundError`, as someone with no role on the plant. `PlantLife.plant` has no plant row to lock, so `CareStore.lockAndLoadForPlanting` reads the accounts the new row names (its creator, and its owner when a user owns it) `FOR KEY SHARE` right after the owner lock. A missing one is refused as `CreatorGone` and answers the `UnauthorizedError` of a request with no account behind it. The command then applies the rules of `src/contexts/care/domain/decide.ts`, `src/contexts/care/domain/life.ts` or `src/contexts/care/domain/plan-decide.ts`, writes, and publishes what happened on the topic `care`. Reminders consumes that topic and replans by itself, and `src/events/care-forwarder.ts` turns the facts the app listens to into EventBus events. So no caller of a Care command calls `Reminders.request` for what the command changed, or publishes a care event. `linkToMessage` is the one exception to the shape. It is a single statement on a column no rule reads, with no plant lock and no fact. `CareReads.due` is the read side for due cares. `CareLogRepository`, `CareScheduleRepository` and `CarePlanRepository` only read.

A day is stored, not derived. The due day of a schedule is `plant_care_schedules.due_day` and the day of a care is `care_logs.care_day`. The store writes both in the plant's care timezone, and a stored day stays put when the owner changes timezone. Read a day from its column with `CareDay.make` instead of computing it from `next_care_at` or from `date`, and filter due days with `dueOnOrBefore` in `src/contexts/care/stored-day.ts`. Both columns are `NOT NULL` since migrations `0080` and `0081`, so an insert into either table names its day column, in a test and in a seed script too.

The health of a plant is stored as a condition: `THRIVING`, `HEALTHY`, `SICK` or `RECOVERING`. Since migration `0082` the `plant_health` type has no `NEEDS_ATTENTION`. `seePlantCare` in `src/contexts/care/plant-care.ts` derives it from overdue care when a plant is read, so only an answer carries it. Type a stored health as `PlantCondition` and an answered one as `PlantHealthStatus`.

The assistant reaches `CarePlans.propose` through its chat tools in `src/services/ai-chat/tools/index.ts`. `buildPlantChatTools` gives a chat about one plant `createDiagnosis`, `proposeCarePlan` and `searchPlantKnowledge`, with a `PlantPermit<'chat'>`. A general chat gets only `searchPlantKnowledge` from `buildGeneralChatTools`, because a plan needs a plant. The treatment steps of `createDiagnosis` become a proposed plan linked by `diagnosisId`. A plan has at most `CARE_PLAN_MAX_STEPS` steps (`packages/shared/src/domains/care-plan/schema.ts`). A step's `dueInDays` resolves from the user's local midnight in `ToolDeps.timezone`. Its `careType` moves a real schedule when the plan is accepted, so `src/services/ai-chat/tools/care-plan-step-schema.ts` makes the model choose `none` for every step that is not literally a watering, feeding, misting or repotting.

Do not write `care_logs`, `plant_care_schedules`, `care_plans` or `care_plan_steps`, insert or delete a `plants` row, or give `died_at` a value, outside `src/contexts/care/store.ts`. Care must not load `src/contexts/canopy`, `src/contexts/absence` or `src/contexts/reminders`, directly or through a module it imports. `src/__tests__/architecture/context-boundaries.test.ts` fails on each of these, and on an import of `src/contexts/reminders` or `src/events/index.ts` from a plant life endpoint. A new refusal does not compile until `errorOf` in `src/contexts/care/refusals.ts` gives it an error. A new life state does not compile until `LIFE` in `src/contexts/care/domain/life.ts` has its cell, and a new plan command or status until `RULES` and `DEAD_PLANT_TAKES` in `src/contexts/care/domain/plan.ts` have theirs. A new fact does not compile until `staleAfterCare` in `src/contexts/reminders/triggers.ts` says what it makes stale and `src/events/care-forwarder.ts` says what the app hears. Terms are in `CONTEXT.md`, section Care.

### Dead plants

A plant with `died_at IS NOT NULL` is in the user's cemetery. It keeps every row (schedules, photos, care logs) and takes part in no care task, reminder, digest, nudge, user-facing count or Live Activity. It accepts no new care, no correction, no schedule change, no due-day move and no plan command except `CarePlans.delete`, and a proposal for it answers as a plant that does not exist. Its past cares can still be edited or removed.

- Apply `isLivingPlant()` or `livingPlantSql` from `src/repositories/helpers/living-plant.ts` to every new query that joins or counts `plants` for one of those paths. For a `leftJoin`, put the predicate in the join condition, because in the `WHERE` it drops the rows without plants.
- `PlantRepository.findAll` with `filter: 'dead'` lists the cemetery. Every other filter is living-only unless the caller passes `includeDead: true` (admin).
- The lifecycle endpoints (`markPlantDead`, `revivePlant`, `deletePlant`) take the plant and a permit from `withPermittedPlant(id, 'markDead' | 'revive' | 'delete')`. Their `PlantLife` command publishes `PlantLifeChanged`. Reminders replans from it, and the forwarder turns it into `PlantLifecycleChanged`, which the Live Activity subscriber uses to refresh the card. Delivery drops any other notification of a dead plant (`plant-gone`).
- `plant` and `revive` add a living plant to an owner, a user or a Canopy. They take the `OwnerHeld` proof that `withOwnerLock` gives its body, and the endpoint asks `LimitChecker.checkPlantLimit` under that lock. Revive restarts every due day at today plus the schedule's frequency, in the plant's care timezone.
- Achievements (`countPlants`), admin analytics, and care-log history and streaks count dead plants on purpose. Past care stays history.
